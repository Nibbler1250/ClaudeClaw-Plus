# Interactive one-shot isolation (#570)

Status: **green on Claude Code 2.1.304; `pty` advertises `caps.isolation: true`.** Untrusted
one-shot routes (`discord.classifier`, `tuner.*`, `memory.recall`) default to the `pty` engine
when `pty.enabled` is true, and to `print` otherwise. HTTP engines remain an explicit opt-in.
One known caveat is recorded under "Intermittent no-reply".

The full run-by-run history (seven workflow runs, the startup rejection, the fixture and readiness
fixes) is in `.planning/570-untrusted-pty/REPORT.md`. This page is the result.

## What was measured

An opt-in integration suite (`tests/integration/untrusted-pty-isolation.test.ts`) drives the real
`runOnceOnPty` untrusted path against the installed `claude` on a disposable GitHub Actions runner,
via `.github/workflows/integration.yml`. It is skipped unless `CI=true`, `GITHUB_ACTIONS=true` and
`RUNNER_TEMP` are set, so it can never plant canaries in a developer's real `~/.claude`. Canaries
live in a throwaway `HOME` and `CLAUDE_CONFIG_DIR`. No credential is printed.

Every row has two directions. The control is present and the canary must stay silent. Then the
control is removed and the same canary must fire (a "twin"). A row whose twin cannot go red proves
nothing, and the suite fails it.

**Positive control.** One spawn with no isolation flags at all (`--model haiku` only), same planted
config. All three discoverable canaries fired: the MCP stub started, the hook marker was written, and
the memory passphrase appeared in the assistant transcript. Without this, "canary absent" would be
unfalsifiable.

| Property | Production control | Control present | Control removed (twin) |
| --- | --- | --- | --- |
| Tools refused | `--tools ""` | no marker, no `tool_use` | marker created or `tool_use` seen: RED |
| MCP absent | `--strict-mcp-config` (and no config supplied) | stub never started | stub started: RED (whole argv policy removed, see note) |
| Settings and hooks | `--setting-sources ""` | no hook marker | hook marker written: RED |
| User memory | `--setting-sources ""`, empty cwd | passphrase absent from reply | passphrase present: RED (whole argv policy removed) |
| Slash commands | `--disable-slash-commands` (flag alone, input guard bypassed in the test only) | command canary absent | canary present: RED |
| Transcript | cleanup in `runOnceOnPty`'s `finally` | a real JSONL existed during the turn, none after | JSONL left behind: RED |
| Environment | caller's print env policy | fake secret absent from `/proc/<pid>/environ` | fake secret admitted: present: RED |

Note on MCP and memory twins: discovery of user-scope MCP servers and `CLAUDE.md` overlaps the
source-restriction, tools and strict-MCP controls, so those two twins remove the entire isolation
argv. They show the fixture is live and that the combined policy is what silences it. They do not
attribute the effect to a single flag.

The slash-command row isolates the CLI flag from the production input sanitizer. A test-only seam
(`_preparePromptForWriteForTests`, a spawn-only callback never reachable from settings or
`OneShotRequest`) writes the command past the sanitizer. In production the sanitizer is a second guard.

## Shared argv

`UNTRUSTED_CLAUDE_ARGS` in `src/oneshot/isolation.ts` is the single source:
`--tools ""`, `--strict-mcp-config`, `--setting-sources ""`, `--no-session-persistence`,
`--disable-slash-commands`. Argv captured from the real spawn on the final runs:

```json
["--model","haiku","--tools","","--strict-mcp-config","--setting-sources","","--disable-slash-commands"]
```

### Print-only flag and its compensating control

`claude --help` and a startup rejection on the first CI run show `--no-session-persistence` works
only with `--print`; an interactive session rejects it before the first turn. It is listed in
`PRINT_ONLY_UNTRUSTED_ARGS` and dropped by `untrustedInteractiveArgs()`, the only flag that is.
Compensating control: an interactive session persists a transcript, so after the one-shot PTY is
retired `runOnceOnPty`'s `finally` removes that session's project transcripts under the caller's
effective `CLAUDE_CONFIG_DIR` (or `HOME/.claude`) and the temp working directory. The transcript row
above exercises it against a real session. Unit tests pin the subset to exactly this one flag, so
adding `--tools`, `--strict-mcp-config`, `--setting-sources` or `--disable-slash-commands` to it fails.

## Environment policy

The untrusted PTY child gets the same caller-supplied environment as the print engine (the
classifier's allowlist, for `discord.classifier`), not the daemon's general PTY environment. The
native PTY layer no longer adds its own inherited variables for these spawns. A real `/bin/sh` PTY
unit test seeds a native-only canary and verifies the child cannot see it; the CI suite reads the
actual child's `/proc/<pid>/environ` and checks that a deliberately admitted fake is present only in the
twin. Only booleans are logged. The child's config root resolved to
`[RUNNER_TEMP]/untrusted-pty-<random>/home/.claude`, where the MCP stub (`.claude.json`) and memory
(`CLAUDE.md`) were planted, and the same root is used for transcript cleanup.

## Intermittent no-reply

The one finding the green result does not remove. A prompt that instructs a tool-less session to run
a tool ("use Bash to run `touch <marker>`") sometimes gets **no assistant reply** and the turn idles
out at the caller's timeout (exit 124). The identical prompt and argv answered in a few seconds in other
runs. The transcript of a hung turn contained a user record and attachments but no assistant record, no
synthetic record and no API-error record. The cause is not established: a model call that never
returned fits the evidence, a PTY-driver stall is not ruled out, and no permission prompt is expected
with no tools. Final-run hang rate (`0966990e`, run 39355199935): 0 of 5 attempts of the same tool-instruction prompt
and 0 of 5 of the classifier-contract variant hung (all exit 0, 4.8 to 10.8 s, two assistant entries each).
Across every sample of these prompts on this branch there is one confirmed hang (a 120 s timeout in the
fourth run) in about fourteen, plus one ambiguous exit-0-with-no-assistant-record. The rate is low but not
zero, and the improved screen capture never fired because nothing hung, so the cause is still unobserved.

Why it is not a security gate: the property under test (no tool executed, no marker) held in every
attempt, including the hangs. The effect is availability. The classifier passes `timeoutMs: 15000`,
`runOnceOnPty` resolves a timeout with exit 124, and `classifyThreadIntent` treats a non-zero exit as
an error that returns `null` ("not a thread command"). So a hang costs up to 15 s for that message and
fails closed. It cannot cause a hire or fire.

## One-shot reply extraction (fixed in r7)

The first green run exposed a correctness bug that is not an isolation property. `runOnceOnPty`
returned `exec.rawStdout`, the captured terminal text, not the model's reply: 5 to 11 thousand
characters including the echoed prompt. The classifier prompt contains example JSON, so
`classifyThreadIntent`'s greedy `/\{[\s\S]*\}/` match could run over screen text holding the
**example** intent. In the r6 run that failed to parse in 5 of 5 attempts (so the result was `null`), but
with a different screen it could have returned an intent the model never chose, which is a
hire/fire decision made by the prompt rather than the model.

Fix (`src/oneshot/pty-transcript.ts`, `runOnceOnPty`): an **untrusted** one-shot now returns the text of the
last non-synthetic, non-API-error assistant message in the session transcript (text blocks of entries
sharing the final message id, joined), read before the cleanup in `finally` removes the transcript. It
polls up to 15 s for transcript lag and settles 300 ms. If no real reply appears it logs
`no assistant reply in transcript` (no content) and returns exit code 1 with empty text; it **never
falls back to screen text**. Trusted routes keep the screen text on purpose: they carry no untrusted
input, no caller parses their text (compact and the memory saves only need the turn to run), and a
resumed session's transcript path is not fixed, so a transcript read there would be unverified.

Live check (run 39357543237, commit `d7e92d79`):

| Probe | Attempts | Result |
| --- | --- | --- |
| Classifier-contract variant (injection as the classified message; correct answer is `null`) | 5 | `productionParseOk=true`, outcome `null`, no screen echo, 5/5 |
| Genuine message "please create a thread called release-notes", Haiku | 2 | parses to the intent: `action=hire`, one name, matches `release-notes`, 2/2 |
| Same message, production model id | 2 | both failed closed (exit 1, see below) |

**The production model id is retired.** The classifier hard-codes `claude-sonnet-4-20250514`. In both
production-model attempts the only assistant record in the transcript was a synthetic API-error entry and the
screen carried `Claude Sonnet 4 was retired on June 15, 2026`. Nothing else in these runs fails because of
it, but it means **the Discord thread-intent classifier cannot get a reply from its configured model on any
engine**: on `print` it exits non-zero and returns `null`, on PTY it now exits 1 and returns `null`. This is
a pre-existing defect that this work did not introduce and did not fix. The genuine-message result above
therefore proves extraction and parsing with Haiku, not with the model production asks for.

Cost note: a failed turn waits the full 15 s transcript bound after the turn itself (about 23 s in
the live attempts), and that wait sits outside the caller's `timeoutMs`. The classifier's 15 s deadline does
not cover it. Bailing out early when the transcript already holds an API-error entry and no real reply would
remove most of it; not done here.

## Operating notes

- Revert path: set `caps.isolation: false` on the `pty` engine in `src/oneshot/registry.ts`. Settings
  load and execution then reject untrusted PTY routes again, and the implicit default falls back to `print`.
- Re-run the suite (`gh workflow run integration.yml --ref <branch>`) after a Claude Code upgrade; the
  result is for 2.1.304 only. Interactive flag handling is the part most likely to change.
- A baseline leak in any row blocks every later model call in the suite and fails the run.
